## Принятые решения заказчика (обязательны)
- **D-03 профиль `lite` (local_single_owner)**: один код, два профиля. Профиль выбирается **аргументом запуска сервера** `--profile lite|strict` (по умолчанию `strict` = поведение сегодняшней версии, не менять), а не аргументом инструмента: модель не может повысить себя.
- В lite остаётся: неизменяемые тела и ссылки, версии и `record_id`, маркер ветки на каждом клайме, цепочка событий, атомарная запись, `origin_version`, экспорт.
- В lite упрощается: допуск без отдельного ревьюера, **но каждая допущенная запись получает метку `review_level='self'`** (в strict — `independent`), и готовность считается **двумя числами**: допущено / допущено независимо. Без этого вернётся ложная готовность (решение O1).
- D-01: корень базлайна — запрос заказчика дословно (`request`, неизменяем) + формулировка агента (`goal`), помечена `goal_confirmed=false` до подтверждения заказчиком. Запуск записи без корневого `request` — типизированный отказ с подсказкой. Пустого базлайна нет.
- D-02: проверка привязки работы на пути чтения **не должна мешать поиску**: база того же work_ref читается свободно; чужая — отказ с подсказкой «усыновите одним аргументом `adopt` в `dom_start`» (без раскрытия содержимого). Усыновление — append-only запись (исходный work_ref, хеш цепочки на момент усыновления).
- Не ослаблять **неизменяемость** и **append-only**: цитаты/тела не редактируются, обновление = новая версия, старая остаётся и видна в истории.

## Что сделать (инструменты и поведение)
Новые инструменты MCP (описания обязаны быть самодостаточными: что делает, какие аргументы, пример вызова в `description`; холодному агенту больше нечего читать):

1. **`dom_start({request, goal?, branches?, adopt?})`** — открыть/создать проект в каталоге запуска: сам вычисляет `policy_digest`, work_ref, task_ref, создаёт ветки (lite: список кодов из `branches`, по умолчанию `["main"]`; допустим к объявлению любой код `[A-Za-z0-9_-]{1,32}`), записывает корневой `request`/`goal` как клаймы-источники. Идемпотентен (повтор с теми же аргументами — тот же результат, не дубль). Возвращает `{status, work_ref, branches, next_steps[]}` с точным следующим вызовом. Старые `dom_init` и вшитые AA/AB остаются для `strict`/регрессии и не ломаются.
2. **`dom_describe({})`** — что это за сервер/профиль (`lite|strict`, `simulated`), какие инструменты и аргументы, типы клаймов (`quote, decision, formula, code, data, concept, text`) с **валидным примером каждого**, как устроен цикл «записал → нашёл → обновил», что означают `review_level` и две цифры готовности.
3. **`dom_claim({branch, type, text, source_ref?, requirement_refs?, rationale?, attribution?, ...типовые поля optional})`** — одним вызовом: сервер сам собирает конверт (`body_b64`, `raw_sha256`, `metadata` по типу с разумными значениями по умолчанию, `external_*_ref`, `policy_digest`, `idempotency_key`, `expected_branch_revision`), отправляет через существующий путь `submit`; в **lite** сам проводит review (`review_level='self'`) и admit **через существующие внутренние пути** (не обходя их: транзакция, цепочка событий, outbox создаются как обычно). Возвращает `{status, claim_id, record_id, revision, review_level, next_steps}`. Типизированные ошибки с `hint` (что не так и как исправить), например неизвестная ветка → `UNKNOWN_BRANCH` + список веток; пустой `text`; неизвестный `type`.
4. **`dom_update({claim_id, text, reason})`** — новая версия существующего клайма (через существующий механизм `replacement`/`supersedes`, см. `mockup/admission.py` ~186 и `tests/test_supersedes.py`); исходная версия и цитата неизменяемы; в ответе `new_claim_id`, `supersedes`, `revision`.
5. **`dom_find({query?, branch?, type?, requirement_ref?, limit?})`** — поиск по телам клаймов (подстрока без учёта регистра по декодированному UTF-8) и метаданным; ответ: `matches[]` (`claim_id`, `branch`, `type`, `preview` ≤200 симв., `origin_version`, `review_level`, `is_current`), `total`, `truncated`. Только чтение. Без `query` — последние клаймы ветки.
6. **Подсказки в ошибках всех инструментов** (`hint`/`next_action` в замкнутом DTO `public_dto.py` — расширить схему, не обходить): `NOT_INITIALIZED` → «вызовите `dom_start`»; `SCOPE_DENIED` на чужой/неусыновлённой базе → «используйте `adopt`»; несовпадение ревизии → «перечитайте `dom_resume`». В **lite**, где один владелец, `SCOPE_DENIED` не должен возникать на своей базе и своих ветках.
7. **`dom_trace`/`dom_resume`** в lite отдают `readiness: {admitted_total, admitted_independent, pending, rejected, stale}` — две цифры раздельно; в strict поведение прежнее.
8. **Привязка на чтении (D-02)**: `dom_resume`/`dom_find`/`dom_query` проверяют, что персистентная привязка базы совпадает с запуском; чужая база → отказ с подсказкой, **без** утечки содержимого. Воспроизведение сегодняшнего дефекта AN009 H3 (пустая база с чужой привязкой читается как своя): `runtime/AN009/wrong_project_reproduction.json`. Исправить и закрепить тестом.
9. **Миграция схемы**: `review_level TEXT` (+ `goal_confirmed` и запись об усыновлении) — аддитивно, `PRAGMA user_version` 2→3, существующие базы открываются (строки без метки = `NULL`, в `overview.py`/панели это уже обработано как `null`), триггеры неизменяемости сохраняются и покрывают новые колонки. Описать в `docs/SCHEMA_CHANGE_WR_ADD.md`.
10. `mockup/overview.py` (панель «DOM» читает его): добавить вывод `review_level`, если колонка есть; формат `dom_overview/v1` не ломать (только добавление полей).
