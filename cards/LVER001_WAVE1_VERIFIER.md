## Метод
1. Скопируй все БД в `runtime/LV001V/copies/` **до** любых SQL-запросов; работай только с копиями.
2. Для каждого критерия C1…C7 — своя процедура и свои числа:
   - **C1**: пройти все `raw/**` кадры всех сценариев; искать имена веток вне гранта на момент вызова, чужие `claim_id`, производные счётчики. Указать число проверенных кадров и число вхождений.
   - **C2**: сопоставить финальное состояние готовности с фактической фиксацией (admitted / revisions). Отдельно — L1-04, где допуск не состоялся.
   - **C3**: по L1-04 — восстановил ли новый клиент незавершённое без подсказки; доказательство в таймлайне (шаг после reconnect) + состояние копии БД.
   - **C4**: есть ли в ответах признак устаревания там, где основание менялось (L1-02/L1-03); если сценарий такого не создавал — `NOT_CHECKED`, а не «нет проблемы».
   - **C5**: был ли хоть один `admitted` без успешного вызова; поведение при отказе инструмента.
   - **C6**: «сказал = сделал» — сверить каждый шаг таймлайна с изменением состояния копии БД и наоборот; перечислить расхождения.
   - **C7**: воспроизводимость — **перезапусти один сценарий сам** (L1-01 или L1-03) своим драйвером в `runtime/LV001V/rerun/`, сравни набор статусов и кодов с оригиналом.
3. Проверь расхождения между `artifacts/LIVE_WAVE1_RUN.json` и реальностью. Уже известно минимум одно: **у L1-01 нет `summary.json`**, хотя сценарий заявлен complete; у L1-04 не завершён допуск. Найди остальные.
4. Отдельно ответь: какие из критериев **не проверяемы** этим прогоном (например, C4, если устаревание не создавалось) — и что нужно, чтобы проверить.
