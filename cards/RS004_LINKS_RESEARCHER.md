### Q-L2-05 (сужение Q-L2-02 на ДВА отдельных механизма)

Заказчик дословно: «если мы похожесть используем для проверки клайма ветки для новой версии- то мы проверяем только ветку версий этого клайма- если мы проверяем существование клаймов то мы проверяем по существующим клаймам их наполнению и ключевым словам?»

Это два РАЗНЫХ механизма с разным scope, которые Q-L2-02 не развёл:

- **(А) Проверка новизны версии** — перед допуском новой версии (`extend_leaf`/`fork_sibling`, RS003 DL-04/Q-L-05) — есть ли уже содержательно совпадающий tip в ТОЙ ЖЕ `family_id`? Сегодня этого НЕТ вообще: CAS проверяет только `expected_tips_digest` (не протухла ли ревизия), не содержательное совпадение с существующим tip. Агент может заявить `extend_leaf` поверх уже существующего идентичного по смыслу tip, и система это не поймает.
- **(Б) Проверка существования дубликата где угодно** — есть ли ЛЮБОЙ видимый клайм (не обязательно той же семьи), говорящий то же самое, по содержанию/ключевым словам? Это кросс-family граф похожести из прежнего Q-L2-02.

Задача: дать РАЗНЫЕ механизмы для (А) и (Б), не один общий. Для (А) — где именно в admission-пути нужна проверка (перед или вместе с CAS), какой вид совпадения считается «тем же самым» (байт-точное? требует человеческого суждения?), что происходит при обнаружении (тихий REJECT? предупреждение с обязательным подтверждением?). Для (Б) — унаследовать scope-вопрос Q-L2-02 (per-family vs cross-family), но теперь явно отдельно от (А).

- **why:** AN004 слил in-family novelty check и cross-family duplicate detection в один вопрос; это два разных admission-time механизма с разной ценой ошибки.
- **expected_answer_type:** engineering_requirement для (А) P0-сценария; needs_user для scope (Б), наследует прежний Q-L2-02.
- **verification:** (А) — подать `extend_leaf` с телом, идентичным текущему tip семьи → должен быть пойман (какой код отказа?); физическое доказательство — raw admission response. (Б) — дифференциальный oracle по образцу L1-L8 на существующих клаймах разных семей.

### Q-L2-06 (причинная реконструкция: коррекция плана vs уже существующий форк)

Заказчик дословно: «фактически корекция плана это новая версияя клайма ? а если были подвижки и там уже ветки наплодились? то это форк?вероятно да. причем тут важно указать время... иначе не будет ясно что было первым курица или яйцо.»

Разбор оркестратора (не окончательный, подлежит проверке RS004): коррекция внешнего пункта плана OMH сама по себе НЕ создаёт новую версию клайма — она делает существующий pin (Q-L2-03) протухшим (`pin_behind`). Тип подаваемой В ОТВЕТ новой версии (extend_leaf/fork_sibling) определяется состоянием `tips` семьи НА МОМЕНТ ПОДАЧИ, не природой причины (`reason`-поле уже обязательно в схеме, `dom_contract.py` COMMON/EVENT_FIELDS). Сырые данные для восстановления порядка событий уже есть — каждое событие несёт точный серверный `server_time` (`admission.py:206`), не заявленный отправителем. НО отдельного отчёта/запроса, который восстанавливает причинную последовательность («правка плана была раньше или позже, чем расхождение семьи клаймов»), в коде НЕТ.

Нужно: точный механизм причинной реконструкции — при обнаружении `pin_behind` (Q-L2-03) система должна отдавать не просто флаг, а сравнение точных таймстемпов (момент захвата исправленного пункта плана vs момент допуска КАЖДОГО существующего tip семьи), чтобы можно было доказательно ответить «что было раньше» без догадок. Разобрать: достаточно ли сравнения raw `server_time`, или нужен отдельный тип события для фиксации самого факта «план скорректирован, обнаружено после допуска N tips» (чтобы не восстанавливать это каждый раз запросом, а зафиксировать разово).

- **why:** заказчик указал на реальный пробел — причинность должна доказываться точным временем, не порядком обращения/близостью событий; без этого отчёта «курица или яйцо» неразрешима доказательно.
- **expected_answer_type:** engineering_requirement, тесно связан с Q-L2-03 (один и тот же pin-механизм).
- **verification:** создать клайм с pin на пункт плана → подать независимое уточнение той же семьи (до правки плана) → затем скорректировать план → третий кандидат должен получить отчёт с точным порядком трёх событий по server_time, не только флаг stale; физическое доказательство — три raw timestamp, явный diff порядка.
