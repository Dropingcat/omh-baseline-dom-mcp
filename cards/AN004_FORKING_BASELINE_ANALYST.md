## Оркестраторские находки, которые нужно ПРОВЕРИТЬ И КРИТИЧНО РАЗОБРАТЬ, а не принять на веру

Все пронумерованные ниже утверждения — выводы оркестратора ТЕКУЩЕЙ сессии, сделанные по чтению кода и API, НЕ готовые решения. Аналитик обязан перепроверить их адресно (своим чтением source/API), а не пересказать.

- **F1 (code: `mockup/admission.py:190`, `claims` CREATE TABLE в `storage.py`).** `record_id` — единый глобальный UUID на всё хранилище, НЕ партиционирован по AA/AB. AA/AB — scope-ветки допуска/видимости задачи, не копии клайма. Уникальность ID чисто механическая генерация, без проверки совпадения с существующим содержимым; контентной уникальности нет вообще.
- **F2.** Из этого следует: ничто в коде не предотвращает появление двух content-идентичных клаймов с разными `record_id` в AA и в AB независимо — ровно зазор, который должна закрывать сходимость (RS003 Q-L-07/DL-06), а не сама identity-схема.
- **F3 — НОВЫЙ риск, не разобранный в AN003/RS003.** Если граф похожести по keywords (Q-L-11, RS003 NU-01) способен строить связи МЕЖДУ разными `family_id` (а не только внутри одного дерева), подсказка «похоже на...» в видимой ветке потенциально раскрывает факт существования клайма в невидимой ветке — риск того же класса, что TD-DOM-19 (hidden-branch metadata leak), но через keyword-similarity-канал, не через граф связей. RS003 Q-L-09/10/14 явно этот канал не разбирали.
- **F4 (API: `tool_describe(omh_todo)`, `todo_store.py:97-161,493-519`, `todo_reconciliation.py`).** У отдельного пункта плана OMH todo НЕТ стабильного ID/дайджеста. Адресация — порядковый номер (`item: int`) + проверка совпадения НАЧАЛА текста (`item_text` prefix) при `advance`; при расхождении — отказ («stale index»). Операция `set` ПОЛНОСТЬЮ заменяет список — не включённые пункты выпадают, без истории. Единственный существующий дайджест (`todo_items_digest`) считается по ВСЕМУ списку целиком (используется только для протухания `deferred_reason`), НЕ по отдельному пункту — не пригоден как внешний pin.
- **F5, вывод из F4.** Наивная привязка клайма DOM к «номеру пункта плана OMH» ломается при любой перестройке/переформулировке плана без предупреждения. Для надёжной сшивки клайм должен при создании сохранять точный текст/хеш пункта плана на момент привязки (аналогично существующей проверке `SOURCE_BYTES_MISMATCH` у цитат, `dom_contract.py:112`), а изменение текста пункта должно детектироваться как `pin_behind`/stale, не оставаться незамеченным.
- **F6.** Ингестии плана OMH в клаймы сейчас НЕТ в коде — предложение, не реализация. Подтверждено прежним RS001-материалом (не найдено противоречий при текущем чтении).

## Задача анализа

1. **FORKED как «естественный механизм».** Разобрать причинно: расщепление — это следствие ЯВНО заявленного намерения (`extend_leaf`/`fork_sibling`, RS003 DL-04), а не самопроизвольный побочный эффект. Критически сравнить это с формулировкой заказчика «должен быть естественный механизм» — выяснить, не подразумевает ли заказчик автоматическое обнаружение расщепления БЕЗ явного намерения подающего (это другой, более рискованный механизм: тихое обнаружение конфликта смысла без декларации намерения). Дать точный вопрос Q-L2-xx RS004: если автоматическое обнаружение расщепления всё же нужно (без обязательной декларации intent) — на основе какого критерия и кто несёт ответственность за ложное срабатывание/непойманный случай.
2. **Identity и граф похожести — проверить F1/F2 своим чтением кода** (не доверять пересказу), подтвердить или уточнить. Для F3 — явно оценить, насколько keyword-similarity-канал относится к тому же классу риска, что TD-DOM-19, и сформулировать точный вопрос RS004 по scope-ограничению похожести (внутри одного `family_id` только, или допустимо шире при каком условии).
3. **Сшивка с планом OMH (F4/F5/F6)** — перепроверить API своим вызовом/чтением (`tool_describe`, `todo_store.py`, `runtime_reader.py`), не повторяя слепо находки оркестратора; если подтверждается — сформулировать точные требования к DOM-стороне привязки (что именно клайм обязан сохранить о пункте плана при создании ссылки, как обнаруживается расхождение) и точный вопрос RS004 по механизму самой сшивки (нужен ли отдельный снимок текста пункта внутри клайма, в каком поле, когда считается stale).

Q-L-07) — не предлагать слабее уже спроектированного.
5. Как и раньше: НЕ отвечать на вопросы вместо RS004, не внедрять код, не трогать продукт. Для каждого пункта — точный вопрос с ID (Q-L2-01... и далее), источник/причина, ожидаемый тип ответа, предполагаемая проверка (action→expected→physical evidence) для будущего RS004.
