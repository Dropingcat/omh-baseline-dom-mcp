## 1. AU006-F-01 [blocking] — где нет обязательной сверки

**Цепочка (mockup):** `dom_init` (admission.py:104-110), `dom_submit` (:119-143), `dom_review` (:164-173), `dom_admit` (:175-220).

- **`init`** проверяет только: simulation-флаг (иначе `OMH_BINDING_UNVERIFIED`), форму `{external_work_ref, policy_digest}`, scope, policy. Пакет/квитанцию базлайна не выдаёт.

- **`review`**: независимость root, digest. Базлайна нет.
- **`admit`**: `STALE_REVIEW` по **заявленным** dependencies (:186-187), `REVISION_CONFLICT`, повторные проверки. Условия «выдан и прочитан» нет.

**Минимальные точки-носители** (что проверить, где жить):

| Слой | Точка | Доказуемо без живого хоста? |
|---|---|---|
| DOM | `submit/admit` требуют обязательный `receipt_id` (в ENVELOPE dom_contract.py:6 сегодня нет → `UNKNOWN_FIELD`, dom_contract.py:71) | Да: поле отсутствует, тест с ним → REJECTED |

**Что такое «сверка» (три раздельные стадии, нельзя приравнивать):**
1. **Получение пакета** — выдача BaselinePacket с `receipt_id` и хешем (PLAN_IDENTITY:155). Доказывает **доставку**, не понимание.

**Граница доказуемого без живого хоста:** доказуемо — отсутствие механизма в source, отсутствие инструментов, wire R01/R02 (обе ветви DEMO_ADMITTED), обход stale через `dependencies={}`. **Не доказуемо** — порядок хука до/после dispatch, fail-open/closed живых хуков, возможность отказа старта, выбор «хук vs обёртка».

## 3. AU006-F-03 [major] — дерево ready_for_owner_review

**Текущая формула** (admission.py:281-283): `ready = not blockers and bool(traces)`, где blockers = `CRITERIA_NOT_CURRENT|CONFLICT|BRANCH_NOT_CONVERGED|SYNC_PENDING`. `owner_close_called` всегда False (:283).

## 4. AU006-F-04 [major] — что не отдаёт dom_resume

`resume` (admission.py:383-392) возвращает **snapshot + trace + sync + read_snapshot**. Пending-кандидаты (id/digest/payload/key) — **не возвращаются**: запросов в candidates нет, discovery API отсутствует (server.py:36-134). Это **отсутствующая функция**, не проекция: resume построен как «снимок+статус известной ветки».

**Минимум новому клиенту:** endpoint/поле, перечисляющее authorized pending (id, intent_digest, branch, author, payload-ссылку), чтобы он мог продолжить **без старого idempotency key**.

**Отличие от kill-recovery:** R05 — старый клиент **как процесс** сохранял payload+key и переиграл тот же key; это память клиента, не discovery. `resume_after_kill.json` подтверждает: только snapshot/trace/sync, candidates отсутствуют. Durable SQL не решает потерю базлайна без API.

## 5. AU006-F-05 [major] — todo_evidence не доказывает DOM-работу

**Механизм** (todo_evidence.py): `item.evidence={kind,ref}`; kinds: `tool_call` (terminal exit_code==0), `file_write` (bytes_written / success), `pr/ci_run/team_check` (не резолвятся). `EVIDENCE_TOOLS=(terminal,write_file,patch)` (:94-98). Привязка — **по окну времени** (window), не по содержимому (:53-59); текст команды/вывод/ответ не читаются (:61-62). `window_empty` **закрывает** пункт (:140,427).

**Нужно для связи с DOM-результатом:**
- новый evidence kind (`dom_result/dom_admit`, ref=tx/receipt_id),
- резолвер по реальному admitted tx, а не exit_code,
- критерий закрытия = admitted+delivered результат (O3),
- window-привязка остаётся, но не достаточна: нужен task-специфичный признак,
- `window_empty` не должен закрывать DOM-обязательные пункты,
- MCP-only window (REJECTED) не засчитывать.

**«Активность» vs «работа» без LLM:** детерминировано — наличие admitted tx/claims/outbox ack, тип результата, соответствие окна пункта; суждением остаётся семантическая достаточность (независимый проверяющий, PLAN_IDENTITY:176-178).

## 6. NU-AU006-01 — последствия (а)/(б)/(в) + 4-й вариант + LLM-only

Оси: ложный DONE / потеря работы / тихое расхождение / стоимость / аудитор.

| Вариант | Ложный DONE | Потеря работы | Тихое расхождение | Стоимость | Аудитор |
|---|---|---|---|---|---|
| **(а)** только материальные | невозможен | возможна («в стол» = F-03) | низкий, но неотличимо от молчания | малая | «работа без учёта; возможна потеря» |
| **(б)** офлайн-журнал + сверка | невозможен (PROVISIONAL) | минимальна | **высокий** без перепроверки | высокая | «второй путь; слепое воспроизведение» |
| **(в)** всё стоп | невозможен | не применимо | низкий, но обход через терминал остаётся | минимальная | «fail-closed корректен, гарантия иллюзорна» |
| **(г)*** явная регистрация «вне базы» + авто-подъём | невозможен | низкая (манифест) | низкий | средняя | «учтено как вне-базы; поднято только подтверждённое» |

**Проверка «не упущен ли 4-й вариант»:** (**г**) существует и **не упакован** как отдельная справочная строка в DECISION_NU (там он представлен как рекомендация «(а) как база + узкая часть (б)», DECISION_NU:62-64, и как замечание к (а) про статус «вне базы», :23). Мой вывод: (**г**) = (а) + обязательная видимость + манифест для авто-подъёма; **не** (б), т.к. нет второго канала записи фактов. Он устраняет главный минус (а) — неотличимость от молчания. Дальше вариант выделен в JSON `decision_matrix.NU-AU006-01.variants[3]` для сравнения.

**Недоступность только LLM** (отдельный случай): DOM-недоступность = нет сервера (некому выдать пакет/допуск/доставку; данные SQLite целы). LLM-недоступность = код работает (admission.py детерминированный, LLM в admit-пути нет), но встают **суждения**: converge/классификация влияния/достаточность/FORKED-NEW_VECTOR. Правило: без суждения — только PROVISIONAL, никакой автоматической сходимости (DECISION_NU:66); нельзя запрещать чтение/фиксирование хода (TBO-09:43). Для LLM-случая (в) избыточен (запись возможна), актуальны (а)/(б).

## 7. NU-AU006-02 — состав изолированного эксперимента

**Цель:** измерить свойства **хоста** (не DOM). Гипотезы и прогоны:

| # | Гипотеза | Прогон | Доказано, если |
|---|---|---|---|
| H1 | хук старта до первого инструментального вызова | изолированный профиль; замер позиции в dispatch | подпись хука раньше первого материального вызова |

| H3 | хост может отказать в старте без базлайна | задача без BaselinePacket | реальный block ИЛИ задокументированный allow |

| H5 | изоляция | отдельный профиль/БД/ветка/задача | соседние не затронуты; после — уборка |

**Что доказано:** механизм существует (обязанность из регламента становится свойством), порядок хука, fail-поведение, возможность отказа, числа, изоляция, сценарий для аудитора.
**Что не доказано:** приёмка живым OMH на реальной задаче; обход через terminal/files; другие хосты; полный crash-покрытие.
**Изоляция:** отдельный профиль/воркспейс+SQLite, отдельная ветка/задача, хук только для тестового профиля, kill-switch + TTL, полная уборка. **Стоимость отказа:** F-01 остаётся UNVERIFIED_live; защита → дисциплина агента (то, что AU006 признал несуществующим).
