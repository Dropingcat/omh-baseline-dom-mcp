# DOM ↔ OMH: план документов и исполняемого макета

> For Hermes: выполнять по технологическим картам, исполнитель не принимает себя. Использовать subagent-driven-development: spec compliance, затем quality/security review.

**Goal:** получить начальные документы, закрыть исследованием критические вопросы и собрать проверяемый локальный макет общей DOM-базы с явным маркером ветки на каждом клайме.

**Architecture:** одна база на глобальную работу; OMH владеет задачами/планом/закрытием; DOM — append-only база и веточные срезы. Макет отделяет реальные операции локального хранения от симулированного OMH/Git-доступа. Предложения не выдаются за принятые требования.

**Tech Stack:** устанавливает исследователь по текущей среде; предпочтение Python + SQLite + доступный MCP SDK, YAML-представление без независимо редактируемой второй базы. Никаких установок/изменений live-конфигов без отдельного разрешения.

## Базлайн

Входы: REQUIREMENTS.md (исходные слова заказчика), ADMISSION_AND_INTEGRITY_DESIGN.md (предложение), OMH_CODE_REVIEW.md (статический аудит).

Приоритет: требования заказчика → действующие контракты по роли с явными проектными уточнениями → принятая спецификация → предложения. Кодовая база harness — reference, не объект правки в этом цикле.

## Последовательность

### AA001 — Аналитик

- Карта: cards/AA001_ANALYST.md.
- Прочитать исходные требования и статический аудит; проверить reuse в harness.
- Создать analysis/AA001_ANALYSIS.md и JSON с findings, вопросами исследователю и критерием каждого вывода.
- Приёмка оркестратора: файлы существуют и JSON парсится, критические вопросы и веточный marker не потеряны. Самоотчёт не является независимым APPROVE.

### AA002 — Ресерчер

- После приёмки материала AA001; не параллельно с зависимым анализом.
- Карта создаётся/уточняется в cards/AA002_RESEARCHER.md с точными вопросами AA001 и полным авторским базлайном.
- Сверить идентификаторы OMH и хостовую идентичность, минимальные схемы append-only/branches, реалистичную границу изоляции, digest/revisions/recovery, пригодность локальных зависимостей.
- Создать research/AA002_RESEARCH.md, JSON и source/claim ledger с путями/строками или официальными первичными источниками. Для неизученного NOT_TESTED, не «работает».

### AA003 — Спецификация и план макета

- На основании AA001/AA002 подготовить docs/SPEC.md и docs/IMPLEMENTATION_PLAN.md с конкретными файлами, API, шагами проверки и scope.
- Зафиксировать, что входит в runnable mockup: init, structured rejection, immutable claim with origin_branch, append-only links/comments/properties, candidate/admission bound to digest/revision, retry conflict, scoped branch export, trace/remainder.
- Разделить реальный SQLite/MCP handshake от fake/test OMH/Git adapters. Не генерировать правдоподобные внешние квитанции.
- Если требуется решение заказчика, собрать точную развилку; не блокировать исследование остального.

### AB001 — Исполнитель макета

- Отдельная карта cards/AB001_BUILDER.md после фиксации scope.
- Только prototype/, tests/, examples/ и runtime/ проекта; исходники harness и плагины read-only.
- До реализации отрицательный сквозной сценарий; затем минимальное ядро и CLI/MCP, затем повторить сценарий с физическими артефактами.
- Никакого production enable, авто-merge или произвольного SQL/path API.

### AC001 — Независимая приёмка спецификации

- Отдельный исполнитель, карта cards/AC001_SPEC_REVIEW.md.
- Сопоставить каждый исходный пункт с кодом и фактическим прогоном.
- Проверять НЕсделанное: цитата/ссылка/комментарий mutability, claim-level branch, identity spoofing, stale revision, replay с другим payload, проектный scope, false OMH success.
- Не исправлять код; вернуть APPROVE / REQUEST_CHANGES / BLOCK с конкретными evidence. Возврат воркеру, затем повторная проверка.

### AC002 — Quality/security и независимый прогон

- После соответствия спецификации отдельная карта.
- Проверить качество, ошибки, обходы и воспроизводимость; провести независимый E2E из чистой временной базы внутри runtime/.
- Макет считается макетом, не гарантией защиты от локального администратора или неограниченного terminal.

### Финал

- Оркестратор реально повторяет документированные команды, сверяет артефакты и выводы проверяющих.
- README с одной командой запуска, демонстрацией, картой файлов, ограничениями и остатком.
- Фиксировать точные файлы и статусы; не закрывать master и реальные OMH-задачи в продуктовых системах.

## Режим работы: правила фабрики harness (run mode)

До переноса в плагин оркестратор работает по контрактам harness: `docs/CODERS/06_PIPELINE_ORDER.md` (порядок звеньев), `07_AUDITOR_DILIGENCE.md` (въедливость аудитора, секция 0), `08_ANALYST_RESEARCHER_CONTRACT.md` (аналитик и ресерчер), `09_FINDINGS_ESCAPE_HATCH.md` (классификация находок), `05_REVIEWER_AUDITOR_TECHDEBT.md` (TD), `shared/code-factory-process.md` (контракты звеньев, «LLM свидетельствует, код решает», stop criteria).

Цикл, заданный заказчиком:

```text
план → техкарты → воркер → жёсткий аудит (что НЕ работает)
     → аналитик (почему не работает) → ресерчер (как должно заработать)
     → обновлённый план + техкарта → воркер → ...
```

Артефакты звеньев — `<ROLE>_<BLOCK_ID>.json` в `artifacts/`, отчёты — в `reports/`, рантайм — в `runtime/`. Техдолги — `tech_debt.md` (TD-DOM-NN).

### Положение в цикле

| Стадия | Артефакт | Состояние |
|---|---|---|
| План | `PLAN.md`, `docs/SPEC.md` | есть |
| Техкарты | `cards/AA001…AB001`, новые `AU001`, `AN001`, `RS001` | есть |
| Воркер | AB001-r4: 55 passed, demo exit 0, N1 исправлен | сдано |
| Ревьюер | `runtime/AC001_R2_VERDICT.*` | в работе (передиспатч продолжения) |
| Аудитор | `runtime/AU001_AUDIT.*` | ждёт вердикта ревьюера |
| Аналитик | `runtime/AN001_ANALYSIS.*` | после аудита |
| Ресерчер | `runtime/RS001_RESEARCH.*` | после сводки аналитика |
| Обновлённый план | `PLAN.md` v2 + `cards/AB002_*` | после ресерчера |
| Следующий воркер | AB002 | по обновлённой карте |

Правило при обрыве звена по лимиту итераций: передиспатч продолжения тем же звеном; обрезанный отчёт не является вердиктом (`docs/REVIEW_PROTOCOL.md`).

## Общие запреты

- Никаких секретов, персональных записей или дампов пользовательских баз в примеры.
- Никаких платных моделей/Polza без проверки бюджета и отдельного согласования расходов.
- Никаких скрытых fallback между провайдерами, транспорторами или ролями. Сбой — наблюдаемая причина и согласованный выбор.
- Никакого удаления существующего кода.
- Субагенты получают исходные требования без пересказа, карту инструментов и разрешённую область.

## Текущий физический статус

Начальные документы и карты AA001/AA002 находятся в проекте. Первичный OpenCode AA001 на DeepSeek вернул limit. По требованию заказчика затем проверены GLM → DeepSeek → Flint: первые две вернули limit, Flint canary ответил MODEL_PROBE_OK. Реальная AA001 на Flint не вернула содержательного текста и не создала артефакты, поэтому не принята. Разрешённый fallback: AA001 диспатчен native Hermes subagent с той же картой; task output пока не принят. Платные ключи/Polza не использовались. Остальные стадии не объявлены выполненными.
