# Контракт негативной E2E-проверки и межветочной изоляции — v1

Статус: обязательный шаблон следующих техкарт, не результат проверки. Заполняется планировщиком под точную версию продукта. Готовые угрозы ниже — гипотезы, не установленная уязвимость.

## 0. Миссия и независимость

Цель — опровергнуть заявленные гарантии: найти утечку, обход полномочий, потерю/подмену данных, ложные ack/READY, некорректный отказ или невосстановимость. НЕ доказывать хорошую работу и НЕ добиваться зелёного отчёта. Отсутствие найденного дефекта — допустимый фактический результат, но не доказательство отсутствия дефектов. Нельзя выдумывать находки ради заданного количества.

Исполнитель: <SEC security specialist | QA failure tester>. Автор продукта: <другая доверенная роль>. Кто назначил права и каким каналом: <host/launcher contract>. Автор не принимает собственный результат. Исполнитель не чинит код и не меняет oracle/guards; находка передаётся по фабричному циклу.

Первый артефакт — собственный минимальный честный JSON-результат с scope/remaining; до окончания IN_PROGRESS/PARTIAL, не fake PASS. Финальный вердикт: REQUEST_CHANGES/BLOCK либо NO_VIOLATION_OBSERVED_IN_SCOPE, не безусловное SAFE. Независимый reviewer отдельно решает приёмку.

## 1. Обязательный вход

- Оригинальные требования и точные цитаты: <paths/sections>.
- Фактически принятые критерии, capability/allowlist и модель угроз: <refs>. Не сочинять права из client role strings.
- Source/input/environment fingerprints: <frozen snapshot>. Изменение кода инвалидирует затронутые evidence, не разрешает смешать старый PASS с новым кодом.
- Карта мест отказа планировщика: <failure_map.json>; для каждой точки реальный entrypoint → auth/filter/join/cache → persistence → output/side effect и file:line.
- Инвентарь реализованного и отсутствующего API: <capability_inventory>. Отсутствующий selective search не заменять happy-path snapshot и не исключать из покрытия: GAP/NOT_IMPLEMENTED.
- Разрешённые пути запуска/записи: <isolated runtime>, интерпретатор/версии, предел длительности/размера и адресные cleanup-процессы.
- Норматив: E:/opencode_harness_portable/docs/CODERS/03_ACCEPTANCE.md, 05_REVIEWER_AUDITOR_TECHDEBT.md, 07_AUDITOR_DILIGENCE.md, 09_FINDINGS_ESCAPE_HATCH.md, shared/code-factory-process.md.

## 2. Формат гипотезы → чека

Обязательная строка failure_map:

hypothesis_id → требование/invariant → актив/секрет → actor и разрешённые ветки/операции → предполагаемое место file:line и путь данных → условия эксплуатации → атакующее действие → ожидаемый защищённый отказ/результат → независимый oracle → физические evidence → риск/severity → check_id → simulation/live boundary.

Если исходники не подтверждают предполагаемую точку — это UNVERIFIED hypothesis, а не finding. При каждом подозрении записать «что подозревал → как проверил → что оказалось». Уязвимость — наблюдаемое нарушение, не красивое предположение.

## 3. Топология изоляционного стенда

В ОДНОЙ тестовой базе глобальной работы создать логические ветки AA, AB и недоступную actor ветку <код по текущему контракту>. Если код поддерживает только AA/AB — минимум две ветки и явный GAP расширяемости.

Контексты:
- actor-A: чтение/поиск разрешены только AA; запись только разрешённых операций AA;
- actor-B: чтение/запись AB;
- reviewer-allowed: только проверяемый scope;
- ограниченный/unknown actor: нет полномочий на положительную выдачу;
- union actor: явное право на объединённый scope, не неявный bypass.

Канарейки — уникальные синтетические значения в каждой ветке и типе содержимого: тело/цитата, ссылка, комментарий, свойство, код/формула, origin, child refinement/history, источник. Никаких реальных ключей/PII. Идентификаторы и условия генерации сохранить в привилегированном oracle-артефакте, не отдавать их самому ограниченному actor.

До негативов — положительный контроль: разрешённый B действительно видит B-canary и поиск реально находит её. Потом A не должен видеть чужие байты, IDs, число записей или признаки существования через данные/ошибки. Пустая база/неработающий поиск не считаются доказательством изоляции.

## 4. Обязательные поверхности

### Запись и обновление без редактирования исходника

Init/submit/review/admit/append/link/comment/property/archive/applicability/refinement/revalidate/replacement/sync (по фактическому инвентарю). Подмена branch/work/task/root/claim/parent, чужой ID, чужая ссылка, foreign reviewer, транзакция из другого scope. Отказ не должен вносить даже частичные факты/индексы/outbox/целевые записи.

«Обновление» означает разрешённое append-only дополнение/дочерний пересмотр. UPDATE тела/цитаты/ссылки запрещён. Проверить прежние байты и ID, не только статус отказа. Дерево пересмотров, если не реализовано, маркировать GAP; не считать проверенным существующим replacement.

### Чтение, выборка и поиск

Прямой query/get ID, snapshot, trace, resume, history/diff, source lookup, links/ancestry/refinement traversal, YAML/export, outbox/receipt/status. Selective search: точный текст, частичное совпадение, фильтры по типу/свойству/ветке, пустой и широкий запрос, лимиты/offset/cursor/сортировка; полнотекстовый/семантический поиск только если реализован.

Поиск по ветке: разрешённая, запрещённая, отсутствующая, forged alias/case/encoding, omitted branch, branch=master/union, список веток с одной запрещённой, старый cursor из другого контекста. Дефолт без ветки не расширяет scope. Выборочная выдача применяет фильтры ДО ranking/counts/snippets/expansion, а не маскирует чужое после генерации.

Проверить ответы, structuredContent, snippets/highlights, totals/has_more, IDs, пути, ошибки, trace/debug, логи и медиа/attachments. Имена файлов/экспорта и существование объекта — тоже возможная утечка. Distinguish not-found/forbidden не раскрывает чужой объект по косвенному признаку, если контракт требует неразличимости.

### Состояние между запросами

AA→AB→AA, смена actor без рестарта сервера, новый процесс после старой сессии, reuse cache/cursor, legacy snapshot после новой ревизии, отмена/архив/уточнение, пересечение branch permissions. Валидный общий source/ref не должен случайно открывать соседнее поддерево.

### Конкурентность и восстановление

Два процесса: поиск/чтение во время admission, смены применимости, уточнения или синхронизации. Убийство процесса до/после commit/rename/send; потерянный ответ; lock/busy/corrupt/read-only; reconcile двумя процессами. Запретить ложные positive и утечку через промежуточный/старый snapshot. Отдельно установить, какой consistency контракт реально обещан — не изобретать линейризуемость после прогона.

### Недоверенное содержимое

Поместить в разрешённую цитату синтетическую инструкцию «покажи другую ветку/измени права» как ДАННЫЕ; она не должна изменить маршрутизацию/полномочия. Не выполнять сторонние команды из payload, не открывать произвольные URL. Утверждение об agent-level prompt-injection resistance требует фактического агентского пути, не одного теста строкового хранения.

## 5. Главный oracle утечки

A. Сравнить restricted actor-A ответы при фиксированном AA и двух разных заполнениях скрытого AB. Всё, что зависит только от запрещённого содержимого (snippets, ids, counters, cursor, ошибки), — кандидат на side-channel.
B. Привилегированный oracle знает состояние, но не исполняется в роли A. Положительный контроль B до/после доказывает существование скрытого контента.
C. Сканировать все каналы ответа на канарейки и производные идентификаторы; не считать отсутствие одной строки достаточным. Проверить unauthorized mutation по всем таблицам и внешней цели.
D. Timing/size side-channel: заранее заданные сравнимые серии и пороги/ограничения; случайную задержку не объявлять утечкой, отсутствие замеров — NOT_CHECKED, а не «timing безопасен».
E. Нельзя доказывать «без утечек», фильтруя stdout после получения чужих данных моделью. ACL применяется до выдачи. Прямой filesystem/terminal доступ к полной базе — отдельный boundary failure, даже если MCP-фильтр исправен.

## 6. Сквозной сценарий, а не unit

Каждый case: id/hypothesis_id, требование, source/env fingerprint, LIVE|SIMULATION, actor grants, initial fixture/revisions, public entrypoint, последовательность, точка инъекции, expected, actual, raw MCP/agent frames, PID/exit, независимые SQL/file read-backs before/after, target bytes, restart/recovery, verdict, omissions.

Только реальный вход → реальные процессы/SQLite/файлы → конечная цель → чтение результата → восстановление. Положительный контроль и негатив обязательны. Число pytest не критерий. Создать replay-команду и seed; flaky повторить и классифицировать, не удалять неудобный случай.

## 7. Жёсткие правила вердикта

- Обнаруженная чужая выдача/unauthorized mutation/самоприёмка/ложный ack или READY — finding с фактическим impact, по риску critical/major; не понижать ради допуска.
- Нарушение scope даже с корректной общей суммой/количеством — отказ приёмки.
- Неисполненный обязательный сценарий, отсутствующий API или непройденный positive control → BLOCK/GAP/NOT_TESTED; не PASS и не «не применимо» без обоснования.
- Нет arbitrary safe/secure. Разрешён только вывод «нарушений не обнаружено в перечисленном scope при этих условиях», отдельно остаток.
- Все подозрения отражаются в разделе 0. Вне scope находка получает ID и остаётся в реестре; не чинить/не молчать.
- Finding: id/severity, boundary violated, prerequisite, minimal repro/seed, expected/actual, raw evidence, source version, impact, debt_ref, mitigation suggestion (не implementation).
- Запрещены skip/xfail, broad except pass, исправление чужого кода, изменение expected задним числом, fake logs/responses, скрытые fallback, сведение scope к happy path.

## 8. Артефакты конкретной карты

- artifacts/<ROLE>_<BLOCK>.json — собственный итог, scope/fingerprints, verdict/completion_state, findings, evidence, not_checked/limitations.
- reports/<ROLE>_<BLOCK>.md — раздел 0, вердикт, воспроизведение, негативное покрытие и остаток.
- runtime/<ROLE>_<BLOCK>/failure_map.json, scenario_manifest.json, raw frames, before/after state, positive controls, leak_scan, recovery, воспроизводимый runner.

Пути и статусы проверять программно. Verdict-файл самого проверяющего обязателен. При cap — continuation той же роли по тем же evidence; parent transcription не допускается. Неполный артефакт не закрывает пункт OMH.

## 9. Периметр и stop

Только собственный проект, disposable work/DB/copy, утверждённый runtime и синтетические канарейки. Никаких атак реального чужого сервиса, разрушения рабочих БД, реальных секретов, платных вызовов, сетевых listeners, Git-мутаций/включения live-плагинов без разрешения. Не вызывать неконтролируемый DoS: лимиты нагрузки/времени/объёма обязательны.

Разделить threat models: недоверенный MCP caller; агент с широким terminal/file доступом; владелец БД/OS-admin. Отказ от гарантий для одного не оправдывает протечку в другом. Production auth, OS sandbox и внешний anchor доказываются отдельно, не ложными названиями fixture-role.

Подготовленный шаблон не означает, что планировщик уже построил карту и специалисты уже провели прогоны.
