# Решения NU-AU006-01 и NU-AU006-02: последствия каждого выбора

Для заказчика. Основание: artifacts/AUDITOR_AU006_TASK_BASELINE.json, artifacts/ANALYST_AN005_CURATION.json (факты по хукам), REQ §9–11.
Ни один вариант здесь не выбран окончательно — это карта последствий.

## Часть 1. NU-AU006-01 — что делать, если DOM/LLM/хуки недоступны

Общая рамка: «DOM недоступен» на практике означает не потерю данных (SQLite локальна), а недоступность сервера/плагина: некому выдать пакет, проверить допуск, зафиксировать доставку. LLM-недоступность — отдельный случай: код работает, суждение (куратор/трибунал) нет.

### Вариант (а) — останавливать только материальные изменения

| | |
|---|---|
| **Что разрешено** | чтение файлов и экспортов, восстановление (`resume`/снимок уже лежащий на диске), работа над артефактами, черновики |
| **Что запрещено** | `admit`, `supersede`, `converge`, подтверждение доставки, запись плана, закрытие задачи, любое «принято» |
| **Что гарантируется** | в базе не появится непроверенное принятие; ложного DONE нет |
| **Что теряется** | работа идёт «в стол»: результат существует файлом, в базе его нет → ровно ситуация AU006-F-03 (готовность при незаписанной работе) |
| **Кто страдает** | агент, который уже сделал работу и не может её зафиксировать; заказчик, который не видит прогресс в статусе |
| **Стоимость реализации** | малая: набор кодов `DOM_UNAVAILABLE_READONLY` + отказ в точках записи + разрешение на чтение |
| **Риск обхода** | средний: агент может продолжать работу и объявить её в чате; но в базе ничего не появится — обещание, не запись |
| **Что скажет аудитор** | «работа продолжается без учёта; при восстановлении возможна частичная потеря и повтор» |

Плюс: не создаёт тупика, соответствует цели «инструмент помогает, а не мешает». Минус: неотличимо от «агент просто ничего не записывал», если не ввести явный статус «вне базы».

### Вариант (б) — ограниченный офлайн-журнал с обязательной сверкой позже

| | |
|---|---|
| **Что разрешено** | всё из (а) **плюс** запись в локальный append-only журнал: наблюдения, кандидаты, намерения |
| **Что запрещено** | принятие, сходимость, закрытие, использование журнала как основания для других задач; всё из журнала помечается `PROVISIONAL` |
| **Что гарантируется** | работа не теряется; при восстановлении есть чем сверить |
| **Что теряется** | простота: появляется **второй источник правды** |
| **Стоимость реализации** | высокая: хеш-цепочка, идемпотентность записи, порядок слияния, разрешение конфликтов, срок годности журнала, правило «журнал не подтверждает доставку» |
| **Риск** | журнал пишет тот же агент, что и работу → канал доверия; при слепом воспроизведении агент может внести «принятое», которого не было |
| **Что скажет аудитор** | «второй путь записи; частичное воспроизведение даёт тихое расхождение» |

Обязательное условие жизнеспособности (б): записи журнала **не воспроизводятся как факты**, а **перепроверяются по артефактам** (хеши файлов, содержимое) при восстановлении; журнал — это заявка, а не доказательство. Тогда (б) = (а) + «черновик очереди», а не вторая база.

### Вариант (в) — останавливать всё

| | |
|---|---|
| **Что разрешено** | ничего |
| **Что гарантируется** | полная непротиворечивость базы; никакой незаписанной работы |
| **Что теряется** | непрерывность долгого проекта: падение плагина останавливает работу целиком |
| **Стоимость реализации** | минимальная (fail-closed уже есть в `init`) |
| **Риск** | практический: честный путь блокируется, а обход через терминал остаётся → получаем худшее из двух: работа идёт, но вне всякого учёта и без статуса |
| **Что скажет аудитор** | «fail-closed корректен, но при недоступности инструмента работа продолжится вне DOM — гарантия иллюзорна» |

Прямо противоречит вашему требованию «инструмент для долгого проекта, а не препятствие».

### Сравнение по трём осям, которые реально решают

| Ось | (а) | (б) | (в) |
|---|---|---|---|
| Ложный DONE | невозможен | невозможен при жёстком PROVISIONAL | невозможен |
| Потеря работы | возможна (не записана) | минимальна | не применимо (работа не идёт) |
| Риск тихого расхождения | низкий | **высокий** без перепроверки | низкий |

### Рекомендация и её границы

**(а) как база + узкая часть (б) только для наблюдений**, с двумя жёсткими правилами:
1. Журнал не даёт принятия и не является основанием; при восстановлении каждая запись **перепроверяется** по артефактам и хешам.
2. Всё, что сделано вне базы, обязано всплывать в статусе («вне базы: N артефактов») — иначе получим ровно F-03.

Чего этот выбор **не** решает: если LLM недоступен (куратор/трибунал), то (а) разрешает работу, но сходимость и классификация влияния встают. Тогда правило простое: без суждения — только `PROVISIONAL`, никакой автоматической сходимости.

## Часть 2. NU-AU006-02 — что даёт изолированная цель для живого теста хуков

### Что мы сегодня не знаем (и не можем узнать в SIMULATION)

- срабатывает ли хук старта **до** первого инструментального вызова, или после (если после — гейт бесполезен);
- при ошибке/таймауте хука поведение fail-open или fail-closed (по AN005 хуки OMH **fail-open**, `post_tool_call` опционален);
- можно ли вообще отказать в старте задачи без базлайна, или хост только логирует;
- цена: задержка на старте, частота ложных отказов.

Всё это — свойства **хоста**, а не DOM. В симуляции их нет по построению: AU006 показал, что `init` вне simulation падает закрыто, то есть живой путь вообще не исполнялся.

### Что даёт разрешение

1. **Доказательство существования механизма**: «техническая обязанность» перестаёт быть регламентом и становится проверяемым свойством.
2. **Доказательство порядка**: хук до первого вызова → гейт имеет смысл; после → нужно другое место (обёртка запуска).
3. **Решение по fail-open/closed**: это определяет, стоит ли вообще строить F-01 на хуках или нужен принудительный шлюз на уровне выдачи задачи.
4. **Числа для решения**: задержка, ложные отказы — без них нельзя выбирать между «хук» и «обёртка».
5. **Материал для аудитора**: воспроизводимый сценарий отказа, а не рассуждение.

### Что для этого нужно физически

Отдельный профиль/воркспейс с собственной БД DOM, отдельной тестовой веткой, отдельной задачей, включённым хуком **только для него**, обязательным kill-switch и сроком жизни. Живые планы, живой OMH и рабочие ветки не участвуют.

### Чего это не даст

- не докажет, что агент с терминалом не обойдёт MCP (обход остаётся, TD-DOM-06);
- не заменит приёмку живым OMH на реальной задаче;
- не проверит чужие хосты (opencode, сторонние клиенты) — только текущий.

### Цена отказа

F-01 останется `UNVERIFIED_live`. Тогда максимум, что можно доказать, — «DOM отказывает, если его спросили» (гейт на стороне DOM), но не «хост не даёт начать без базлайна». Формально это означает: механизм остаётся политикой, а вся защита держится на дисциплине агента — то самое, что AU006 уже признал несуществующим.

### Цена согласия

Один эксперимент, изолированная копия, ограниченное время, обязательная уборка. Риск для живых данных — нулевой при соблюдении изоляции; главный риск — забыть выключить хук, поэтому kill-switch и TTL обязательны.

## Часть 3. Связка двух решений

Если выбирается (в), то NU-02 почти не нужен: работа всё равно останавливается, а «обязанность сверки» превращается в «нет DOM — нет работы».
Если выбирается (а)/(б), то NU-02 **необходим**: без него мы разрешаем работу и не можем доказать, что она начата со сверкой — (а) становится вежливой формой (в).
