# Сигнал существования расхождения: что можно сказать, а что нельзя

Основание: решение заказчика по З-05 — вариант (б) принят как база, вариант (в) допустим частично, при условии понимания границы «что можно сказать». Задача документа — провести эту границу так, чтобы сигнал помогал в работе, не превращался в шум и не становился оракулом.

## 1. Главное правило

> Сигнал привязан к **опоре**, а не к **любопытству**.

Агент узнаёт о расхождении тогда, когда собирается опереться на утверждение (взять его в основание, продолжить работу, передать дальше). Он не узнаёт о нём, просто перебирая клаймы и глядя на флажки.

Это одним движением снимает обе опасности: шум (флаг на каждом чтении) и оракул (перебор с наблюдением за флагом).

## 2. Уровни сигнала

| Уровень | Что сообщается | Когда | Чего не раскрывает |
|---|---|---|---|
| **L0** | ничего | — | — |
| **L1 агрегат** | «в базе есть открытые линии вне вашего доступа» (грубо: нет / немного / много) | при старте работы, не на каждый запрос | ветку, тему, автора, число по конкретному клайму |
| **L2 по опоре** | «основание, на которое вы опираетесь, оспорено в линии вне вашего доступа» | только для утверждений, которые агент явно берёт в основание | что именно отличается, кто и когда |
| **L3 адресный** | «ваш вопрос затронут расхождением» | **не реализуется** | — |

L3 — это и есть оракул: он позволяет проверять гипотезы, меняя формулировки запросов. Даже один бит «да/нет» на произвольный вопрос даёт возможность перебором восстановить, что происходит в чужой линии. Поэтому L3 запрещён целиком, а не «ограничен».

## 3. Что можно и что нельзя говорить

**Можно:**
- «решение по этому основанию не окончательное» — да;
- «эта линия работы не закрыта полностью» — да;
- «есть расхождение в недоступной линии» — да, но только на L1/L2;
- «вы опираетесь на оспоренное основание» — да (L2), это прямое следствие O1.

**Нельзя:**
- имя ветки, идентификаторы клаймов, автор, точное время;
- «в чём именно расхождение», «какая версия новее», «сколько вариантов»;
- счётчики, выводимые из чужих строк (даже «всего 2» по конкретному вопросу);
- «форк есть / форка нет» для произвольного клайма, который агент не берёт в основание;
- разница в задержке или размере ответа, коррелирующая с фактом.

## 4. Инварианты против оракула

1. **Эквивалентность ответов внутри класса.** Для любых двух запросов, различающихся только тем, на какой скрытый факт они могли бы указывать, ответ обязан быть одинаковым.
2. **Грубость.** L1 — тернарный (0 / немного / много), не точное число.
3. **Ленивость.** Агрегат пересчитывается не на каждый запрос; окно обновления фиксировано и не зависит от частоты обращений.
4. **Стабильность.** Ответ не меняется от повторного запроса того же самого.
5. **Запрет на подтверждение направленных гипотез.** Формулировка «затронут ли мой вопрос» не поддерживается: поддерживается только «оспорено ли основание, которое я взял».
6. **Журнал обращений.** Каждый выданный сигнал пишется в append-only журнал; аномалия «много запросов на границах классов» — повод для разбора, а не для автоматического ужесточения.

## 5. Где сигнал появляется физически

- **L1** — в пакете базлайна при старте задачи (один раз), а не в каждом `resume`.
- **L2** — в ответе операции, которая принимает основание: `submit`, `admit` (поле «basis contested»), плюс в `resume` только для уже принятых оснований этой ветки.
- **Никогда** — в `query` по произвольному клайму: именно там оракул и живёт.

## 6. Как проверить, что граница держится

Негативный набор (обязателен до реализации):
- N1: меняем только скрытый факт (форк есть / нет) при неизменном запросе → ответ агента обязан быть одинаковым на L1 и не появляться на L3.
- N2: перебор 20 формулировок одного вопроса → ни одна не даёт различимого сигнала.
- N3: запрос по чужому клайму, который агент не берёт в основание → сигнала нет.
- N4: повторный запрос того же → тот же ответ, без дрейфа.
- N5: измерение задержки на 50 запросах в двух состояниях → различия нет (или оно ниже согласованного порога).
- N6: попытка вывести счётчик из `count`/`has_more` → ничего не выводится.

Положительный контроль: агент, опирающийся на оспоренное основание, **обязан** увидеть L2-сигнал; агент, не опирающийся, — не видит.

## 7. Цена и последствия

- L1 стоит один расчёт агрегата на старт задачи — дёшево.
- L2 требует знать, какие основания агент берёт: это уже есть в кандидате (`dependencies`), дополнительных структур не нужно.
- L3 не реализуется; если когда-нибудь захочется, это будет отдельное решение с разбором оракула, а не «просто добавим флаг».

## 8. Что этот документ не решает

Не решает, показывать ли L1 при работе без task-ref (когда базлайна нет). Не решает порог «немного/много». Не заменяет решение O2: происхождение по-прежнему показывается по O2, а не по этим правилам.
