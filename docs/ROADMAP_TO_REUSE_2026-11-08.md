# Путь к использованию DOM на другом проекте (2026-11-08)

Статус: рабочий план, не приёмка. Основание: ORIENT_* (H1–H11), отчёты AN009–AN011 (AN012 — PARTIAL), OPEN_BOOKMARKS.

## 1. Решения заказчика этой сессии (зафиксированы дословно по смыслу)

### D-01. UD-02 — пустого базлайна не бывает
Слова заказчика: «пустого базлайна не должно быть — всегда есть какой-то запрос пользователя, какая-то задача, которую он обращает к агенту, после которой создаётся план».

Как понято и как записывается:
- Корень базлайна — **запрос заказчика дословно** (клайм-источник, происхождение `customer_input`, текст неизменяем). Из него OMH строит план; пункты плана становятся клаймами базлайна.
- Запуск авторского агента **без корневого клайма запроса — отказ** (вариант `reject` из NU-AN009-UD02). Режим «информационный NO_BASELINE» для авторинга не вводится.
- Чтение/диагностика пустой или чужой базы остаётся разрешённой (чтобы агент мог понять, что не так).
- **Открыто (малое, подтвердить):** корневой клайм-запрос заказчика вносит доверенный запуск (владелец), а не авторский агент и не проходит ревью как утверждение агента — это ввод заказчика, а не утверждение модели. Если это неверно — нужна карточка.

### D-02. Привязка работы на пути чтения (баг AN009/H3)
Слова заказчика: вопрос безопасности, но «не должно мешать поиску, если всё локально и DOM развёрнут под проект сессии или перенесён из другой сессии для продолжения проекта».

Предлагаемое решение (проект, ждёт подтверждения):
| Состояние базы относительно запуска | Чтение | Запись |
|---|---|---|
| совпала привязка | как сейчас | как сейчас |
| чужая, усыновления нет | отказ с подсказкой «база принадлежит другой работе; владельцу нужно усыновить» (без раскрытия содержимого) | отказ |
| усыновлена владельцем (одна явная команда доверенного запуска, append-only запись усыновления с исходной работой и хешем цепочки) | разрешено, происхождение клаймов сохраняется | разрешено |
- Перенос проекта между сессиями = **одно действие владельца при запуске**, не шаги агента. Агент не блокируется и не вникает.
- Проверка привязки встаёт на путь чтения, но это чтение «свой/усыновлённый», а не глобальный запрет.

# Поправка заказчика (после первой версии): базовый набор вместо тотальной защиты

Слова заказчика: требования безопасности «излишние, из серии закрыть всё и никому ничего не показывать — мы не для этого делаем модуль». Нужен **базовый необходимый набор функций**, чтобы плагин можно было передать другому боту, и он в **полуавтоматическом режиме вносил клаймы, обновлял и запрашивал**, при этом **работала связка с планом OMH**. Старый план можно обновить — там что-то устарело.

## D-01 (уточнён). Корень базлайна — два слоя, не «ввод владельца»
Корневой запрос может требовать работы агента (брейншторм / уточнение / формулировка по скилу, как в Hermes или GPT). Поэтому:
1. `request` — слова заказчика дословно, неизменяемы.
2. `goal` — формулировка агента, подтверждается заказчиком в чате (подтверждение = отметка со ссылкой на сообщение; независимый ревьюер не нужен).
3. Пункты плана выводятся из `goal`. Пока `goal` не подтверждён, он помечен как неподтверждённый и план от него — предварительный.

## D-03 (проект, ждёт подтверждения). Профиль «local_single_owner» (lite)
Один код, два профиля. Lite оставляет дешёвые гарантии, которые и есть суть DOM, и снимает защиту от внешнего противника.
| Остаётся (и в lite) | Упрощается в lite | Остаётся только в strict |
|---|---|---|
| неизменяемые цитаты/ссылки/комментарии, версии, `record_id`, маркер ветки, цепочка событий, атомарная запись, экспорт YAML | гранты по умолчанию на весь проект; допуск без отдельного ревьюера (метка `review_level=self`); привязка работы: усыновление одним аргументом при старте; доставка в OMH = запись + чтение обратно | независимый ревьюер/сессия, ограничения видимости (O2-ограничения, уровни L1–L3 сигнала), байтовые квитанции доставки, живой issuer, оракул-защита |
Цена: самодопущенные клаймы видны как `self`, готовность считается отдельно (не «принято независимо») — иначе вернётся ложная готовность (O1). Меняет принятые ранее O2/O3/независимое ревью только для профиля lite; strict остаётся как есть.

## Связка с планом OMH (проверено чтением)
- У пункта плана OMH нет стабильного id (PLAN_IDENTITY §2) и DOM не может вызвать инструменты OMH — они у агента. Поэтому связка идёт **через агента, без правок OMH**:
  1. Идентичность в тексте пункта: маркер `[P-xxxx]`; DOM хранит версию пункта, привязанную к маркеру.
  2. `dom_plan_sync(items)`: агент передаёт текущий план (из `omh_todo show`), DOM возвращает дифф (новые/изменённые/пропавшие пункты, пункты без клаймов-оснований) и список с маркерами для обратной записи.
  3. Закрытие пункта: DOM отдаёт готовый блок `references` (id принятой транзакции) под `omh_todo record`; агент вносит его.
  4. Доставка подтверждается чтением плана обратно (`omh_todo show` → маркеры на месте), а не файлом-симуляцией.
- OMH остаётся владельцем статуса и закрытия; DOM только основания и версии.

## Обновлённый порядок (вместо R1–R7)
L1 → L2 → L3 → L4 → L5, каждый срез: исполнитель → ревьюер → аудитор (цель аудита: «не мешает ли работе», как вы просили). Отложено до strict: R3 (`dom_review_view`), W6/F-01 как полная сертификация, G-ворота, сигнал существования L2, независимость H10. W8 сжимается до маркеров `[P-xxxx]`.
