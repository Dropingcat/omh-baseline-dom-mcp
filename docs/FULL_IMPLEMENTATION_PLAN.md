## Правила исполнения

Строго последовательно: worker → reviewer → auditor → analyst → researcher → next worker. Ревьюер отвечает за соответствие; аудитор ищет НЕработающее и открывает разделом 0 «подозрение → проверка → результат». Выводы находят отдельные debt ID при обнаружении.

Код пишет воркер; оркестратор готовит/обновляет план и техкарты, диспатчит и проверяет реальные артефакты. Ресерчер не закрывает долг предложением: нужны реализация и независимое подтверждение. APPROVE одного среза не является APPROVE всей системы.

При лимите: передиспатч той же роли с её evidence и точным остатком. Оркестратор не пишет за проверяющего финальный вердикт. Усечённый результат/IN_PROGRESS не закрывают этап. Перед следующим звеном обязательные файлы должны существовать и пройти машинную валидацию.

## Разрешения и внешние эффекты

Разработка и проверки в проекте разрешены; тестовые Git-операции — только в специально созданном локальном synthetic-репозитории в runtime и по карте. Реальный checkout/merge/push пользовательского репозитория, изменение live OMH/плагинов, перезапуск сервиса, публикация и расходы не следуют автоматически из прохождения тестов: перед затрагиванием live-состояния предъявить точный target/change и разрешения, действовать штатными инструментами.

Оригинальные базы/источники не менять; никаких секретов и персональных материалов в synthetic fixtures. OS-admin с полным доступом не считается побеждённым программной цепочкой хешей. Не объявлять полную реализацию при сохраняющейся симуляции обязательного live-порта.

## Решения и остановки

Если исходные требования уже однозначно отвечают на вопрос — привязать решение к цитате, не задавать его заново. Иначе регистрировать точную развилку needs-user, выполнять независимые от неё срезы, не выбирать молча. Лимит — continuation, неисправность — через фабричный цикл, отсутствующее разрешение — явный BLOCK, а не скрытая замена реализации макетом.

## Главный гейт: сквозные боевые прогоны, а не счётчик тестов

Уточнение заказчика — дословно:

делай акцентне на тестики а на е2е прогоны  боевые с вариативностью начальных условий и намеренными попытками вызвать отказ

Приёмка каждого среза — сквозной путь через реальный пользовательский/агентский вход MCP/OMH, реальные subprocess, SQLite и файловую систему до чтения результата в конечной цели и восстановления после сбоя. Компонентные тесты — диагностика/регрессия, их число и зелёный pytest не закрывают критерий.

Матрица обязательных условий:
- Пустая и существующая база; повторная сессия после прерывания; несколько конкурирующих веток; неполный/невалидный вход; устаревший baseline; pending и ambiguous доставка.
- Намеренная смерть процесса до/после COMMIT, до/после rename; занятая/недоступная база; недоступная конечная цель; потерянный ответ после успешной операции.
- Повтор с тем же ключом и изменённым payload; подмена роли/ветки; обход неизменяемости; повреждённый конверт/цепочка; изменение зависимости после приёмки; попытка ложного READY/ack.

На сценарий обязательна квитанция: ID → точные исходные условия и версия → последовательность действий → конкретная точка инъекции → ожидаемый результат → наблюдавшийся результат → проверка конечного состояния/read-back → восстановление → физические evidence. После намеренного отказа проверить отсутствие частично внесённых данных, потерь, дублей и ложной готовности; корректный отказ является успехом защиты, но необработанный crash не объявлять корректным отказом.

Боевой E2E означает фактически работающий маршрут, а не unit с mock-ответом и не нарисованный лог. Если OMH/Git/identity ещё simulation — отметить simulation и не считать live-критерий пройденным. Реальные внешние эффекты и разрушительные пробы только в явно разрешённой изолированной работе/копии; исходные рабочие данные, пользовательские ветки и доступность сервиса не подвергать отказам.

Ревьюер сверяет покрытие базлайна сценариями; аудитор независимо меняет начальные условия и атакует маршрут новыми пробами, а не только повторяет команды автора. Не требовать полного декартова произведения условий; явно обосновать покрытие рискованных сочетаний.

## Дополнительный этап после текущего цикла: негативная сценарная проверка

Прямое поручение заказчика: после текущего цикла планировщик формирует сценарный план и предварительную карту мест отказа/утечек по фактическому коду; эти точки превращаются в checks и E2E-симуляции. Охват: запись, чтение, append-only обновление/уточнение, выборочный поиск, поиск по веткам и утечки из соседних веток.

Подготовлены templates/NEGATIVE_E2E_SECURITY_CONTRACT.md и cards/PL003_NEGATIVE_E2E_PLANNER.md. Очередь в OMH дополнена PL003 → SEC003 → QA003 → независимые review/audit. Этапы pending, не считаются проведёнными. Планировщик запускается после завершения reviewer/auditor/analyst/researcher текущего цикла, не подменяет их.

Вектор — попытаться опровергнуть гарантии, а не подтвердить happy path. Каждая гипотеза привязана к source boundary, субъекту/правам, входу, негативному действию, независимому oracle и физическим evidence. Требуются синтетические канарейки, положительные контроли и проверка всех каналов выдачи, а не только отсутствие одной строки. Отсутствующий API — gap, не укороченный PASS. Специалисты не правят продукт; findings возвращаются по фабрике. Шаблон и записи в плане — подготовка, не исполнение проверки.
