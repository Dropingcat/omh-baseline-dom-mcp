# Протокол независимой приёмки и обрыва агентов по лимиту

Правило заказчика: если проверяющий упал по лимиту, нужен передиспатч для продолжения. Принимать обрезанный отчёт как вердикт — некорректно.

## 1. Кто пишет вердикт

Вердикт пишет только проверяющий, в свой файл (`runtime/ACxxx_VERDICT.md|.json`). Оркестратор не пишет вердикт за него и не «дополняет» его.

Если проверяющий исчерпал лимит до записи файла, это **не вердикт**, а незавершённая работа.

## 2. Что делает оркестратор при обрыве

1. Фиксирует факт: статус `completed` с маркером cap/truncation — не равен «приёмка проведена».
2. Проверяет, какие артефакты реально на диске (пробы, логи, fingerprint), а чего нет.
3. Делает **передиспатч продолжения** тому же проверяющему: узкая цель — «дописать вердикт по уже проведённым пробам, перепроверив ключевые пункты», плюс перечень probe-файлов и findings, которые он уже установил.
4. Если контекст потерян — новый проверяющий получает те же входы и обязан повторить пробы, а не цитировать чужой текст.
5. Транскрипция оркестратора, даже дословная, помечается `NOT A VERDICT` и перекрывается повторным вердиктом.

## 3. Как снижать риск обрыва

- Файл вердикта — **первый** названный артефакт в карте; писать инкрементально (подтвердил пункт — дописал).
- Проверяющему указывать: не перечитывать известные файлы, не делать глобальную разведку, последние вызовы резервировать на запись.
- Давать список конкретных files:line и проб, а не «проверь весь проект».
- Разделять приёмку: соответствие требованиям и quality/security — разные исполнители, каждый со своим вердиктом.

## 4. Состояния, которые нельзя смешивать

| Состояние | Значение |
|---|---|
| self-report исполнителя | заявление, не приёмка |
| отчёт проверяющего без файла вердикта | незавершённая работа |
| вердикт проверяющего в файле | основание для решения |
| решение оркестратора о закрытии | отдельный шаг, опирается на вердикт |

## 4.1. Область вердикта обязательна

Вердикт без указанной области не принимается. Минимум: `artifact_revision`, `scope` (`full` либо перечень проверенных пунктов), `not_checked[]`.

**Вердикт с областью «дельта» закрывает только дельту.** `APPROVE` по исправлению R2-1 не является приёмкой всего артефакта: класс дефектов, не входивший в дельту, остаётся непроверенным.

Практический случай проекта: AC002 проверял только изменения r5 и вернул `APPROVE`; жёсткий аудит AU001 на том же дереве нашёл 4 независимых пути к ложной готовности. Оба вердикта верны в своих областях, но по отдельности создают ложное впечатление принятого артефакта. Поэтому аудит процесса проводится отдельным звеном с полной областью, а не выводится из дельта-вердикта.

## 5. Текущий случай

AC001-R2 и AC002 оборвались на лимите итераций, не записав файлы. Их текстовые отчёты сохранены как транскрипция с пометкой `NOT A VERDICT`. После завершения правок AB001-r4 оба проверяющих передиспатчиваются для записи собственных вердиктов и повторной проверки исправлений.
