# Анатомия клайма в DOM и места маркеров связей — ПРЕДЛОЖЕНИЕ, не реализация

Статус: черновик для аналитика AN003. Реальные поля взяты из mockup/dom_contract.py и mockup/storage.py (макет, SIMULATION). Раздел B — только проект, в коде его нет.

## A. Клайм сегодня — «формула из блоков» (как есть в макете)

```
CLAIM = ⟨ ID ┃ ORIGIN ┃ BODY ┃ TYPE-META ┃ EVENTS* ⟩
```

| Блок | Содержимое | Правило |
|---|---|---|
| **ID** | `claim_id` (server UUID); ярлык `AA001` — это задача, не ID клайма | не меняется |
| **ORIGIN** | `origin_branch`, `origin_version`, автор (principal/root), server time, `tx` | не меняется при переносе, архиве, слиянии |
| **BODY** | `body_b64` (+ `encoding`, `media_type`), `raw_sha256` — цитата / формула / решение / код / данные | **НЕИЗМЕНЯЕМ**, только «архив» |
| **TYPE-META** | по `content_type`: quote{source_ref, locator, source_snapshot_digest} · decision{attribution, rationale, alternatives} · formula{expression, notation, units} · code{repository_ref, relative_path, snapshot_digest} · data{artifact_ref, units, method} · concept{definition, scope, links} · text{classification, evidence} | задаётся при внесении |
| **applicability / requirement_refs** | в каких ветках применим; на какие требования OMH опирается | применимость расширяется записью-событием, происхождение не переписывается |
| **EVENTS\*** | append-only: comment · link · property · applicability · archive · replacement · conflict · resolve · converge · exclude | версия + время + автор; текущее состояние = вычисляется из событий |

Дерево уточнений (4-е уточнение заказчика): `CLAIM ──▶ REFINEMENT₁ ──▶ REFINEMENT₂ …` — каждое уточнение это **новый клайм уровнем ниже** со своей цитатой и атрибутами, последний принятый в ветке = актуальный. В коде пока НЕ реализовано.

## B. Где поставить маркеры связей (предложение)

Принцип из F:\AnalisysDataSet: «заметка = автономный контейнер»; интерфейс — YAML front matter; тип связи — из закрытого словаря (`relation_type.yaml`); обратные ссылки и «соседи» ВЫЧИСЛЯЮТСЯ, а не хранятся (`similarity-analysis.js`, веса в yaml).

```
CLAIM = ⟨ ID ┃ ORIGIN ┃ BODY ┃ TYPE-META ┃ ▶LINKS◀ ┃ EVENTS* ┃ ▷DERIVED◁ ⟩
```

| Маркер | Где живёт | Изменяем? | Зачем |
|---|---|---|---|
| **M1 `basis[]`** — «на чём стоит» | в самом клайме, часть ORIGIN-блока, пишется при внесении | НЕТ (как BODY) | **ответ на «откуда взялось А»**: ссылка на родительский клайм/требование/цитату источника. Лечит потерю базлайна |
| **M2 `refines`** | поле дочернего клайма (узел дерева уточнений) | НЕТ | родитель уточнения; «что именно уточняю/пересматриваю» |
| **M3 `link` (typed)** | событие `link` с `type` из закрытого словаря + `note` | append-only | произвольные поздние связи: `builds_on`, `contradicts`, `confirms`, `uses`… |
| **M4 `accepted_state`** | производное от событий review/converge | вычисляется | «принято / кем / на какой ревизии / проверка ещё свежая?» — чтобы агент видел «А подтверждено», а не переоткрывал |
| **M5 `backlinks`, `neighbors`, `dashboard`** | ▷DERIVED◁: индекс, считается при чтении | не хранится | «карточка чувствует соседей»; НЕ источник истины |

Ключевое правило: **M1/M2 — неизменяемые и внутри клайма; M3 — события; M4/M5 — вычисляемые.** Так не нарушается «исходник не редактируется».

## C. Защита от потери базлайна (мотив 5-го уточнения)

Агент, получив задачу по `A.1`, должен получать не «ссылку на большой документ», а **пакет контекста по связям**: сам A.1 + цепочка `basis`/`refines` вверх + `accepted_state` каждого звена + отметка «закрыто, не переоткрывать без причины». Переоткрытие — только записью события `conflict` с указанной причиной (новое противоречие / ошибка источника / изменение условий). «Не помню, почему А» причиной не является.

## D. Главный риск — НОВЫЙ канал утечки между ветками

Backlinks, счётчики соседей, дашборды и «похожие» — именно то, на чём уже прокололся TD-DOM-19 (метаданные раскрывали скрытую AB). Любое «чувство соседей» обязано:
1. считаться ПОСЛЕ применения grants актора, а не фильтроваться потом;
2. не раскрывать ID, число и существование объектов запрещённой ветки (включая «ещё 3 связи скрыто»);
3. иметь в allowlist DTO (AB003) явные поля, а не свободный dict.
PL003 уже получает это как гипотезу H-LINK (NOT_IMPLEMENTED).

## F. Уточнение заказчика (шестое, дословно в REQUIREMENTS.md) и моё понимание — НА ПОДТВЕРЖДЕНИЕ

Понял так (3 пункта; пометки «?» — где не уверен):

1. **EVENTS делятся на подблоки по универсальным типам задач.** Отдельный подблок «источники/документы»: известные источники, `locality = local | external`. Отдельная **колонка связей**, где живут ключевые слова. (? ключевые слова — свойство клайма для поиска или свойство самой связи/ребра? от этого зависит, где колонка.)
2. **Номер клайма не меняется, но явно указано, к каким веткам он относится** (сейчас это `applicability` как события) **и связи версионные**: ребро графа хранит не просто «клайм → клайм», а «клайм → клайм @ версия ветки», т.е. *с какой ревизией ветки клаймов связан этот клайм*. Следствие: когда ветка-цель уходит вперёд, ребро видно как «привязано к более старой версии» (stale-связь) — тот же механизм, что нужен для устаревших проверок.
3. **Каждое обновление = новая строка в дереве клайма** (append-only), для прослеживаемости. (? различаю две вещи: *строка-событие* — комментарий/свойство/связь/применимость к тому же клайму; *дочерний клайм* — уточнение с новой цитатой по 4-му уточнению. Показывать их в одном «дереве» как производный вид — согласен ли?)

Что это значит для маркеров (дополняет раздел B):

| Маркер | Было | Стало (предложение) |
|---|---|---|
| M3 `link` | событие с `type`, `note` | + `target_claim_id`, `target_branch`, **`target_branch_revision`** (пин версии), `keywords[]` (если ключевые слова на ребре) |
| M6 `sources[]` (новый подблок) | `source_ref` внутри quote-метаданных | вынести в общий подблок для всех типов клаймов: `source_ref`, `locator`, `locality`, `snapshot_digest` (внешний источник без снимка — не неизменяем) |
| M7 `branches[]` (явно) | `applicability` событиями | производный явный список «ветка + с какой ревизии применим», не редактируется, считается из событий |
| Дерево | refinement-клаймы | единый производный вид: события-строки + дочерние уточнения, упорядочены по времени/ревизии |

Риски нового: (а) пин версии → граф «знает» ревизии чужих веток — тот же канал, что TD19 (ревизии скрытых веток); показывать пин только для веток из grants актора. (б) `locality=external` без снимка ломает неизменяемость и воспроизводимость. Оба пункта — вопросы аналитику AN003.
