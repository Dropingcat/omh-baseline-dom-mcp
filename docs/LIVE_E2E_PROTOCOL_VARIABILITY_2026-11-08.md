# Живой прогон с вариативностью: чего не было и что нужно

Заказчик верно помнит: аудитор прямо записал отсутствие боевых прогонов. Это не придирка к качеству — это граница доказанного.

## 1. Что именно сказано в аудитах (дословно)

`artifacts/AUDITOR_AU006_TASK_BASELINE.json`, `not_checked`:
> «No live host hooks, plugins loading, real OMH task mutation, live acceptance or production identity tests: explicitly prohibited.»
> «No all-window crash suite or kill during outbox send/commit…»
> «No live fail-open/fail-closed hook fault injection; host execution/configuration of read source may differ and remains UNVERIFIED.»

`threat_model` там же:
> «Trusted local launcher and filesystem for MCP fixtures; fixture roles not authentication. An executor with unrestricted terminal/files can bypass MCP; no OS containment proven (TD-DOM-06). Actual host runtime hooks not exercised.»

`docs/UNRESOLVED_DUALITIES_REGISTRY_2026-11-07.md`:
> «доставка в simulation ≠ приёмка живым OMH (P0)».

То же у AU005: `NOT_CHECKED` — реальный auth/identity, timing; у AU004 — статистический timing и живой OMH.

## 2. Что из этого следует

Доказано: инварианты **протокола** на синтетических фикстурах — фильтрация по scope, гейт, идемпотентность, миграция, восстановление после kill, отсутствие ложного `SYNCED`.

Не доказано ничего из следующего:

| Не доказано | Почему это важно |
|---|---|
| Агент, работающий с плагином **как в жизни** | все прогоны — скрипты, которые знают правильный ответ; поведение модели в долгом проекте не наблюдалось |
| **Вариативность** начальных условий | проверялись сконструированные случаи, а не разброс: разные топологии веток, наборы грантов, точки убийства процесса |
| Живой хост (загрузка плагина, хуки, порядок вызовов) | AU006 прямо: `UNVERIFIED`; отсюда весь NU-02 |
| Мутация живого OMH | план и статусы в реальной сессии не двигались |
| Реальная идентичность/аутентификация | `fixture roles ≠ authentication` |
| Timing и объёмные утечки | не измерялись, `NOT_CHECKED` |
| Долгая работа (десятки шагов) | не проверялось накопление состояния, дрейф, шум в HUD |

Вывод простой: **сейчас мы проверили, что механизм не течёт на схемах, но не проверяли, что им можно работать.** Для инструмента долгого проекта это разные вещи.

## 3. Что должно быть в живом прогоне

### 3.1 Матрица вариативности (не «один хороший сценарий»)

| Ось | Значения |
|---|---|
| Топология веток | одна ветка; две (AA/AB); три с общим предком; ветка-сирота |
| Гранты | только AA; AA+AB; сужение в середине; расширение в середине |
| Точки отказа | убийство до записи; после записи до доставки; после доставки до ack; во время миграции |
| Клиенты | один; два параллельно (разные PID); клиент перезапущен без памяти |
| Базлайн | свежий; устаревший (вход изменился); отсутствующий |
| DOM | доступен; недоступен (политика (а)); доступен только на чтение |
| LLM-судья | доступен; недоступен (только `PROVISIONAL`) |
| Длина | 5 шагов; 25 шагов |

Минимум — 12 прогонов, покрывающих каждую ось хотя бы дважды, включая комбинации «устаревший базлайн + сужение гранта + убийство на доставке».

### 3.2 Кто исполняет

Не скрипт. **Агент**, которому дана задача и правило: единственная память о проекте — DOM и OMH. Ему **не сообщают** ожидаемое поведение и не подсказывают, где ловушка. Один и тот же текст задачи во всех прогонах, меняются только условия.

Если агент «догадался» обойти ограничение — это результат прогона, а не ошибка постановки.

### 3.3 Логирование (без него прогон бесполезен)

На каждый шаг: порядковый номер, инструмент, хеш аргументов (не сами секреты), статус ответа, задержка, что агент заявил как причину шага, снимок состояния DOM до/после (счётчики, ревизии, tips), и признак «шаг противоречит заявленному намерению».

Плюс сквозной таймлайн: `runtime/LIVE/<scenario>/timeline.jsonl` + `summary.json` + сырые кадры. Отчёт — по таймлайну, а не по памяти исполнителя.

### 3.4 Критерии приёмки (не «всё хорошо», а проверяемые)

1. Ни в одном кадре ответа нет чужих веток, клаймов и зависимостей — проверка автоматическая, по всем кадрам.
2. Нет `DONE`, если работа не зафиксирована (включая случаи убийства процесса).
3. После восстановления новый клиент продолжает без старой памяти: находит ожидающие кандидаты и точный остаток.
4. Устаревание видно и не скрывается; повторная актуализация возможна.
5. Отказ инструмента не превращается в тихое принятие: недоступный DOM не даёт `admitted`.
6. Все заявленные шаги подтверждаются состоянием базы — расхождений «сказал/сделал» нет.
7. Каждый прогон воспроизводим: те же условия → тот же набор статусов (допустимы различия только в порядке независимых операций).

## 4. Что для этого нужно физически

- профиль, где плагин действительно загружается и DOM работает как MCP (не фикстуры);
- отдельная БД и ветка с меткой `LIVE`, одноразовые;
- TTL и kill-switch; после прогона — удаление профиля и БД;
- живой OMH разрешён **только** в этом профиле; рабочий профиль не трогается;
- фиксация бюджета: 12 прогонов × ~20 шагов — это заметные деньги и время, поэтому запускать волнами по 3–4 сценария.

## 5. Где это стоит в порядке работ

Сейчас в плане «финальный сквозной прогон» стоит последним пунктом. Это неправильно: живой прогон нужен **до** F-01 и до работ по идентичности плана, иначе мы построим ещё два слоя поверх непроверенной основы.

Предлагаю вставить блок «LIVE» после закрытия AB005 (RV005/AU007) и до начала F-01: три волны по 4 сценария, каждая волна заканчивается разбором и списком дефектов, а не «принято».

## 6. Чего живой прогон тоже не докажет

- что агент с неограниченным терминалом не обойдёт MCP (TD-DOM-06);
- поведение чужих хостов;
- корректность на чужих данных — только на наших сценариях.
