# Run-mode оркестратора: правила фабрики кода harness

Статус: рабочий режим проекта до переноса в плагин. Источник правил — harness, не собственные догадки:

| Правило | Источник |
|---|---|
| Порядок звеньев | `docs/CODERS/06_PIPELINE_ORDER.md` §2: `worker → reviewer → auditor → analyst → researcher → deployer` |
| Въедливость аудитора, секция 0 | `docs/CODERS/07_AUDITOR_DILIGENCE.md` |
| Роли и материал аналитика/ресерчера | `docs/CODERS/08_ANALYST_RESEARCHER_CONTRACT.md` |
| Эскап-хэтч находок | `docs/CODERS/09_FINDINGS_ESCAPE_HATCH.md` |
| Приёмка по факту | `docs/CODERS/03_ACCEPTANCE.md` |
| Техдолги | `docs/CODERS/05_REVIEWER_AUDITOR_TECHDEBT.md` |
| Контракты звеньев, state machine, «LLM свидетельствует, код решает» | `shared/code-factory-process.md` |

## 1. Цикл проекта

```text
план → техкарты → воркер → жёсткий аудит (что НЕ работает)
     → аналитик (почему не работает)
     → ресерчер (как должно заработать)
     → обновлённый план + техкарта
     → воркер → ...
```

Заказчик задал эту последовательность как рабочую. Она совпадает с 06 §2 с одним уточнением: аудит идёт на негатив, аналитик объясняет причину, ресерчер даёт проверяемый способ исправления.

## 2. Обязательные артефакты звеньев

Каталоги проекта: `artifacts/` (артефакты звеньев), `reports/` (отчёты и журналы), `runtime/` (рантайм, не источник истины), `cards/` (техкарты), `docs/` (план, спецификация, реестр долгов).

Имя файла: `<ROLE>_<BLOCK_ID>.json` (06 §5). Для этого проекта: `worker_AB001.json`, `reviewer_AB001.json`, `auditor_AB001.json`, `analyst_AN001.json`, `researcher_RS001.json`.

Вердикт звена — файл, не сообщение в чат. Отчёт без файла считается незавершённой работой.

## 3. Роли и фокус

| Звено | Фокус | Выход |
|---|---|---|
| Воркер | сделать ровно по карте, не выходить за scope | изменённые файлы + `worker_<ID>.json` + реальные exit codes |
| Ревьюер | соответствие требованиям и спецификации, ложные PASS | `APPROVE / REQUEST_CHANGES / REJECT` + findings |
| Аудитор | **что не работает**: процесс, интеграция, расхождение отчёта и факта. Секция 0 обязательна | вердикт + `TD-DOM-NN` |
| Аналитик | **почему не работает**: систематизация, причины, приоритеты, вопросы ресерчеру | сводка + `analyst_<ID>.json` |
| Ресерчер | **как должно заработать**: проверенные способы, источники, валидация утверждений | findings + `researcher_<ID>.json` |

## 4. Триггеры копания аудитора (07 §2, сокращённо для проекта)

Статус выше факта, расхождение двух копий, двойной источник правды, битый путь, отсутствующий артефакт при заявленном вердикте, ложный PASS, неподключённый файл, отличие от карты, TODO/FIXME, нелогичный diff, счётчики не сходятся.

Сомнение не является результатом. Результат — запись «что увидел → как проверил → что оказалось → что делать».

## 5. Stop criteria и бюджет

Порядок приоритета: `requires_user` → `auditor_block` → `iteration_limit`.
Исчерпание бюджета даёт `BLOCKED` или `PARTIAL`, но не ложный успех (`shared/code-factory-process.md`).

При обрыве звена по лимиту итераций: **передиспатч продолжения тем же звеном**, а не приём обрезанного отчёта и не дописывание вердикта оркестратором (`docs/REVIEW_PROTOCOL.md`).

## 6. Приёмка оркестратора

1. Все названные картой артефакты существуют на диске.
2. Оркестратор сам повторяет документированные команды и фиксирует exit code.
3. Расхождение счётчиков между отчётом звена и прогоном оркестратора — сигнал, что финальный прогон не делался.
4. Три состояния не смешиваются: заявлено звеном / наблюдено оркестратором / принято независимым звеном.
5. Закрытие пункта — только по вердикту следующего звена, не по самоотчёту.
